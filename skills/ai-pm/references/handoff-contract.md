# Handoff Contract — ai-pm → product-feature-helper

ai-pm 侧的**单向契约**：把 ai-pm 前四个 Scene 已经积累的确定性，映射成 product-feature-helper（下称 PFH）产出交互说明文档所需的输入，从而免掉 PFH 第 3 步与第 7.1 步向用户的重复提问。

> **依赖方向是单向的。** 本文件住在 ai-pm 侧，由 ai-pm 适配 PFH。**不修改 PFH 的任何文件** —— PFH 的规则大多由实测事故驱动，改动风险远高于收益。PFH 接口若变化，由本文件跟进；反之不成立。

---

## 何时读这份契约

| 情况 | 怎么做 |
|---|---|
| ai-pm 项目里已经有 `flow.md` 和 `entities.md`，现在要出交互说明 | 按下表逐字段预填，只保留两个需要人的环节 |
| 用户直接单独下单"整理份交互文档"，没有上游 | 走 PFH 原本的第 3 / 7.1 步问答，本文件不适用 |
| 上游只跑了一部分（如有 CUJ 但没有实体状态机） | **逐字段判断**，有上游的字段预填、无上游的字段照常问；不要因为缺一个字段就整张表回退成问答 |

**判定方式：** 逐个字段检查来源文件是否存在且该节非空。存在 → 预填并在给用户的表里标注来源；不存在 → 归入待问清单，一次问完。

## 八个输入字段

下表是本契约的主体。PFH 需要的每个输入，都给出「有上游从哪读」与「无上游问什么」两条路径。

| # | 需要的输入 | 有上游时从哪读 | 无上游时问什么 | 成本变化 |
|---|---|---|---|---|
| 1 | **目标页面 URL** | 立项文档（`docs/01_STRATEGY/`）里记录的产品地址；`docs/04_RESOURCES/` 中的竞品或自家产品链接 | PFH 第 1 步原话：要改哪个页面，要 URL；说明登录页可手动登录 | 问 → **确认**（仍需用户点头，不可跳过） |
| 2 | **改现有 or 新增** | `flow.md` §3 Screen Tree：该屏是否已存在于导航树中 | PFH 第 3 步：改现有内容，还是新增东西？ | 问 → 推导 |
| 3 | **想要什么交互** | `flow.md` §3 每屏的**信息层级**与**主要交互**；`entities.md` 的**操作矩阵**（每状态每角色可做什么） | PFH 第 3 步最贵的一步：请用户截图 + 详述想改成什么样 | 问 → **直接映射** |
| 4 | **流程分几个环节** | `flow.md` §1 CUJ：**一个 journey step = 表格一行** | PFH 第 7.1 步问题 1 | 问 → 直接映射 |
| 5 | **每个环节从哪进** | `flow.md` §3 Screen Tree 上标注的 entry points（`[Entry Point for Journey A]` 这类标注） | PFH 第 7.1 步问题 2 | 问 → 直接映射 |
| 6 | **哪些状态要截图** | `entities.md` 状态表 **×** `flow.md` §3 各屏的**笛卡尔积**，含空态 / 加载 / 报错 | PFH 第 7.1 步问题 3 | 问 → **笛卡尔积** |
| 7 | **描述列：诉求 / 动作 / 规则** | CUJ 叙事（诉求与动作）+ `entities.md` 每条 transition 的 **trigger 与 precondition**（规则与判定条件） | 现场逐条问 | 问 → 直接映射 |
| 8 | **mock 数据长什么样** | Scene 1 的 persona + `docs/00_MEMORY/CONTEXT_SNAPSHOT.md` 里的真实故事 | 临时编 | 编 → **有依据** |

### 字段 6 的展开方式

这是**最精确的一处对应**。`pm-entity` 的 Page Structure Validation 已经在问：

> *"Are there entity states that have no corresponding UI representation?"*

这个检查的答案，**直接就是 PFH 的截图清单**。两个 skill 在各自语境里问的是同一个问题，只是一个为了校验、一个为了截图。

展开规则：

1. 取 `entities.md` 状态表的全部状态（如 `Draft / In Review / Approved / Rejected / Archived`）。
2. 取 `flow.md` §3 Screen Tree 中承载该实体的屏。
3. 做笛卡尔积，**剔除业务上不可能的组合**（如"列表页 × 已归档"若产品规则是归档即隐藏，则剔除并在表里注明剔除理由）。
4. 补上三类**状态机里没有、但界面上一定存在**的状态：**空态 / 加载中 / 报错**。这三类不来自实体状态机，容易漏，必须显式补。

### 字段 8 的取值纪律

从 persona 与 `CONTEXT_SNAPSHOT` 取材，是为了让 mock 数据**像站里真实存在的东西** —— 否则截图没有说服力。同时守住 PFH 已有的两条约束：用**明显是示例但不荒诞**的数据（人名「张三」「李四」、公司「某某科技」），**不要**用「测试123」「aaa」这类一眼假的，也**不要**用真实用户数据（隐私风险）。

## 压缩结果：只剩两个需要人的环节

串起来跑时，PFH 第 7 步原本的流程只保留两处人工环节：

| 保留的环节 | 为什么不能省 |
|---|---|
| **确认目标 URL** | 契约能提供候选，但页面归属与登录态只有用户能确认。PFH 铁律：没问过 URL 就开工，等于交付假结论 |
| **审表结构**（PFH 第 7.2 步） | **唯一一次低成本纠错机会**。截图是最慢的一环，结构错了全部白截 |

其余六个字段全部预填。用户侧体验从"讲清楚你想要什么交互"变成**"审一份已经填好的表"**。

**预填表交给用户时必须标注每行的来源**，例如「阶段 2 来自 CUJ-A 第 3 步」「截图⑤为 Approved 状态 × 详情页」。用户要能看出哪些是从上游推导的、哪些是需要他补的 —— 这是审表能审出问题的前提。

同时照常给出**预计耗时的实数**（按每张截图 1～2 分钟估），不要说"一会儿"。

## 两条路径共用同一个终点

`interaction-doc` 是 brownfield 与 greenfield **共用的终点**，区别只在截图源：

| 场景 | design tokens | 可视状态（截图源） | 交互文档 |
|---|---|---|---|
| **往已有产品加功能**（brownfield） | PFH `design-system.js` 提取真实页面 | PFH 注入真实页面 | `interaction-doc` |
| **全新产品 0-to-1**（greenfield） | 自定，保持设计主张 | `docs/03_DESIGN/screens/` 下的 HTML mockup | `interaction-doc`，**截图源换成 mockup** |

greenfield 场景下的差异处理：

- 截图对象是本地 mockup 文件而非线上页面，`annotate.js` 与 `crop.py` 的用法完全不变。
- 表格「入口」列写 mockup 内的位置（如「首页底部按钮」），不写线上 URL。
- 交付时**必须说明截图来自设计稿而非线上产品** —— 与 PFH「哪些图是 mock 造出来的必须说」是同一条纪律。

## 验证边界

本契约只负责**减少提问**，不负责替用户做决定。三条纪律：

1. **预填不等于已确认。** 每个预填字段都要在审表环节可被用户否决，用户改了就以用户为准。
2. **来源缺失就如实说。** 上游没有的字段，明确告诉用户"这一项上游没有，需要你补"，不要凭上下文猜一个填进去充数。
3. **不要越界宣称。** 契约让表**预填完毕**，不代表交互文档**已验证**。截图与文档的验证边界仍按 PFH 的规则执行：真实页面截过才算在页面上验证过。
