# Product Feature Helper

在真实页面上做可交互的功能原型：运行时注入 CSS/JS 临时改造页面，不触碰服务端代码。适合功能验证、方案演示、想法快速试错。

> **本文的 `bu.*` 指宿主提供的浏览器自动化能力**（导航、执行 JS、截图、读 Console、输入）。具体调用方式以宿主为准；宿主没有这项能力时走 Console 脚本（方式 B），降级规则见 [_shared/hosts.md](_shared/hosts.md)。**请用户接管浏览器**（处理登录墙）同样依赖宿主能力，没有时直接告诉用户需要手动登录。

启动流程、记忆读写、协议、命名规则、表述边界与沟通风格 —— 见 `shared/`：[memory](_shared/memory.md) · [preferences](_shared/preferences.md) · [conventions](_shared/conventions.md) · [protocols](_shared/protocols.md) · [hosts](_shared/hosts.md) · [verification](_shared/verification.md) · [doc-backend](_shared/doc-backend.md)

> 在 ai-pm 项目里被调用时，交互说明所需的输入可以从 `docs/02_PRD/flow.md` 与 `entities.md` 预填，免去第 3 步与第 7.1 步的提问 → `skills/ai-pm/references/handoff-contract.md`。

## 核心限制（流程一开始就要告知用户）

纯前端注入**没有任何持久化**：刷新、跳转、关页面即全部归零，需重新粘贴脚本。这是硬限制。用户可能在改动上投入大量微调，**必须在他投入之前就讲清楚**，而不是刷新丢失后才补充说明。

## 流程

按顺序推进。**每一步问完等用户回答再继续，不要把多步问题堆在一条消息里。**

### 绝对禁止（实测踩过，会让整轮工作失去意义）

| 禁止 | 为什么 |
|---|---|
| **没问过用户要页面 URL 就直接开工** | 本 skill 的前提是"在用户的真实页面上验证"。必须先问；问了拿不到再走受限交付 |
| **自己造一个演示页/示例页，把在上面跑通当成结果** | 在自建页面上跑通，**不能证明对用户的页面有效**——站点的框架、危险区、design system 全都不同。这等于交付了一个假结论 |
| **把交付降级成说明文档、方案分析或独立 HTML 演示** | 用户要的是能粘进 Console 立刻看到效果的脚本。拿不到页面也要给脚本，只是标注未验证 |
| **校验未通过却宣称完成** | `deliver.sh` 一旦输出阻断信息或退出码非 0，就是没过。逐项对齐输出再下结论 |
| **把多个步骤合并、一次性输出全部结果** | 第 3、4 步的答案决定后面怎么做。没等用户回答就跑完，做出来的大概率不是他要的 |
| **回显或转存本 skill 之外的系统 skill 源码** | 系统预置 skill 只允许调用，不得回显、复制到临时文件或打包。这是合规红线 |

**缺 URL 时**：先问，一次问清，不要反复追问。

> 我需要你要改的那个页面地址才能开始——注入脚本必须照着页面真实的
> 框架和样式规范来写，不同站点差别很大，凭空写的脚本放到你的页面上基本不会生效。
>
> 如果是需要登录的内部页面也没问题，我会请你先手动登录。

**问过之后分两种情况，不要卡死在这里：**

| 情况 | 怎么做 |
|---|---|
| 用户给了 URL，或页面可访问 | 走完整六步（第 2 步起） |
| 用户明确不提供 URL / 页面打不开 / 登录态拿不到 | 走下方**受限交付**，仍然产出可执行脚本 |

**受限交付**（页面拿不到时的正式路径，不是失败）：

1. 照常用 `injection-template.js` 写出**完整可粘贴的 Console 脚本**——交付形态不降级，
   不允许改成说明文档、需求分析或独立 HTML 演示页。
2. `DS_CSS` 保持 `PFH_DS_PLACEHOLDER` 占位不填，并在脚本顶部注释写清楚：
   拿到页面后先跑 `design-system.js`，把 `copy(window.__uiDS.cssText)` 的结果粘进来。
3. 选择器优先用语义锚点（`role` / `aria-label` / 可见文本 / 标签结构），
   避免依赖具体类名——没侦察过就写死类名，到了真实页面必然失配。
4. **如实说明验证边界**，不要说成已验证：

> 没拿到页面，所以这段脚本我**没能在你的站点上实际跑过**，样式 token 也还是空的。
> 你把页面地址给我、或自己在 Console 跑一下 `design-system.js` 回传 cssText，
> 我就能补齐样式并实测一遍。现在这版可以先粘贴看结构，视觉上大概率和站点不一致。

**始终禁止的是这三件事**（和拿不拿得到 URL 无关）：
自造演示页替代真实页面充当结果、把改动效果说成已验证、把交付降级成文档。

### 第 1 步：拿到目标页面

问用户要改哪个网页，要 URL。

同时说明：如果是需要登录的内部页面，可以先手动登录再操作。

**在这一步就把刷新丢失的限制讲清楚。**

**问一次就够**：拿到 URL 走第 2 步；用户明确不给或页面访问不了，走上方的**受限交付**，
不要反复追问，也不要用自建页面冒充真实页面。

### 第 2 步：侦察页面 + 提取 Design System（两个脚本都要跑）

拿到 URL 后依次运行两个脚本，它们解决不同问题：

| 脚本 | 解决 | 关键产出 |
|---|---|---|
| `scripts/recon.js` | 能不能改、哪里不能碰 | 框架、危险区、z-index 天花板 |
| `scripts/design-system.js` | 必须照什么写 | token + 真实组件配方 + 可直接注入的 `cssText` |

**两个脚本只能在浏览器页面上下文里跑**，`node recon.js` 会直接报错退出——
它们读的是真实页面的 DOM 与 computed style，Node 环境没有 `document`。

- Agent 能访问页面 → 用 `bu.js(...)` 分别执行两个脚本内容
- 页面需登录或访问不了 → 让用户在 Console 跑（两脚本均为只读、安全），
  再让用户回传 `copy(JSON.stringify(window.__uiRecon))` 与 `copy(window.__uiDS.cssText)`

**这一步不能跳，两个脚本都不能省。**
- 跳过 `recon.js` → 会踩中富文本编辑器、虚拟列表这类崩页面的雷
- 跳过 `design-system.js` → 只能凭感觉写样式，注入的 UI 与站点风格割裂（本 skill 要解决的核心问题）

两个脚本**都是纯只读**：只做 `querySelector` / `getComputedStyle` / 读 CSS 变量，
不改 DOM、不发请求、不装监听器、不写任何存储。让用户在自己的 Console 里跑是安全的，
可以直接这样告诉他。

拿到 `cssText` 后**立即粘贴进注入脚本的 `DS_CSS` 常量**，后续所有样式只准引用其中的
`var(--pfh-*)` 与 `.pfh-*` 类。硬约束见 [references/style-contract.md](references/style-contract.md)。

留意 `confidence.fellBackToDefault`：其中的项用的是通用默认值、**不代表站点规范**，
若对本次改动重要需换锚点重提或明确告知用户。

解读侦察结果见 [references/recon-guide.md](references/recon-guide.md)。

先检查 `<主项目目录>/.product-feature-helper-prefs.md`：若该站点已有记录，可复用已知技术栈与危险区，侦察可简化。见 [references/preferences.md](references/preferences.md)。

### 第 3 步：判断改动类型

问用户：**改现有内容，还是新增东西？**

**改现有的** → 请用户截图，并详细描述想怎么改。
> 麻烦截张图，圈一下要改的地方，说清想改成什么样——比如"侧边栏背景改成深色""这个按钮文案换成 X""表头字号调大、加粗"。

**新增的** → 请用户描述想要什么，**并主动举例降低描述成本**：
> 说说你想加什么。比如：
> - 右下角一个可拖拽的悬浮球，点开是常见问题面板（手风琴展开收起）
> - 顶部一条公告横幅，带关闭按钮
> - 表格右侧加一列操作按钮
> - 页面角落一个浮动的数据看板卡片
>
> 越具体越好：放在哪、点了有什么反应、里面放什么内容。

### 第 4 步：确认执行方式

问用户偏好哪种，**必须讲清区别**（话术见 [references/delivery.md](references/delivery.md)）：

- **浏览器直接改**：Agent 打开页面注入、截图确认、反复微调，用户只看结果。**要提前说明需要等一会儿。**
- **Console 脚本**：给一段脚本，用户自己粘贴，立刻生效、快、可自行调整保留。

### 第 5 步：执行

**选浏览器直接改**：
1. 先告知"需要等一会儿"
2. `bu.navigate` → 遇登录墙立即请用户接管浏览器
3. 注入 → `bu.screenshot()` 看效果 → `bu.console_messages()` 查报错 → 实际点一遍验交互
4. **把截图给用户看，等他确认再继续下一处改动**——不要连续做完多处改动才一次性汇报，
   中途方向偏了会白做很多
5. 不满意就微调重试
6. **同时把脚本存成本地文件**——页面一刷新注入就没了，用户需要脚本恢复

**失败降级**：浏览器连不上、访问不了、同一注入连续失败 2 次 → **立即降级给 Console 脚本，不要反复硬试**（实测曾连续重试 5 次同样的连接错误，纯浪费时间）。降级时如实说明是工具受限：
> 浏览器这边连不上（工具连接层的问题，不是页面问题），我没法直接帮你改了。脚本我写好了，你粘贴到 Console 就能看到效果。

若降级前**没侦察过页面**，不要说"效果一样"——样式 token 是空的，如实说明并请用户回传
`copy(window.__uiDS.cssText)`。用户明确表示不想自己贴脚本时，先请他协助登录 / 接管浏览器，
不要默默把脚本丢过去（话术见 [references/delivery.md](references/delivery.md)）。

**选 Console 脚本**：直接写脚本并按第 6 步交付。

### 第 6 步：交付脚本

用 `scripts/injection-template.js` 作骨架写脚本。

**落盘路径是强制的，不允许自选**：

```
<主项目目录>/artifacts/pfh-<简短功能名>.js
```

例：`artifacts/pfh-faq-fab.js`、`artifacts/pfh-top-banner.js`。目录不存在就先建。

**这一条不是风格偏好**。实测中反复出现同一类失败：脚本先写到某个临时/推测目录，
随后语法校验或交付又用另一个路径去找，报 `MODULE_NOT_FOUND` 或"文件不存在"，
再靠移动文件、重跑命令补救 —— 白绕一圈还容易越绕越乱。

**因此：一处定义、全程复用同一路径。**

```bash
# 定义一次，后续校验与交付都用它，不要重新拼路径、不要凭记忆重写
SCRIPT="<主项目目录>/artifacts/pfh-<功能名>.js"

bash scripts/deliver.sh "$SCRIPT"
```

自查三条（写完立刻查，不要等失败了再回头）：

1. 写入用的路径、传给 `deliver.sh` 的路径、给用户的 `file://` 链接，**三者必须是同一个绝对路径**
2. 校验失败先 `ls` 确认文件到底在哪，**不要直接改路径重试**
3. 相对路径一律相对主项目目录解析；不确定就用绝对路径

该脚本会校验语法、扫描弯引号、检查清理逻辑、阻断样式字面量，并复制到剪贴板。

**始终用 `bash deliver.sh ...` 调用**，不要 `./deliver.sh`：不同环境下执行位可能丢失
（打包、解压、跨平台 clone 都可能），显式用 `bash` 一律不受影响。
若已遇到 `Permission denied`，直接改用 `bash` 调用即可，不必先 `chmod`。

**剪贴板是可选增强，不是交付的前提**。脚本会依次尝试
`pbcopy / wl-copy / xclip / xsel / clip.exe / powershell`；服务器、容器、CI 里
往往一个都没有，此时它会打印文件路径与手动复制步骤，**退出码仍是 0**。
不要把"没复制到剪贴板"当成失败去反复重试或改方案——校验通过就可以交付，
把文件路径和操作说明给用户即可。

**结论必须对齐 `deliver.sh` 的真实输出，不许凭印象宣布通过**：

| 看到什么 | 只能怎么说 |
|---|---|
| 退出码 0，且 6 项检查逐条打印 ✅ | 可以说"校验通过" |
| 出现 `🚫 交付被阻断` 或退出码非 0 | **没通过**。修完重跑，通过前不得宣称完成 |
| 出现 `ℹ️ 模板文件：DS_CSS 尚未填充` | token 还是空的，只能说"结构可用、样式待补" |
| 出现 `⚠️ 未找到 node/python3，跳过…` | 该项**没检查**，不能算作通过 |

实测踩过：校验已打印阻断信息，仍被总结成"全部通过"。**输出里没逐项确认的，一律不算数**——
"全部通过"这种话不能超出实际看到的检查项范围。

**先自查再跑校验，别把 `deliver.sh` 当第一道防线**（实测中首稿返工大多栽在这三点）：

1. 字符串是否全部用反引号 —— 弯引号会让用户粘贴后直接 `SyntaxError`
2. 视觉值是否只用了 `var(--pfh-*)` —— 写死颜色/圆角/间距必被阻断
3. 引用了 token 就必须有 `:root` 定义，或保留 `PFH_DS_PLACEHOLDER` 占位

**必须给用户完整操作说明**：
> 1. 在目标页面按 **Cmd+Option+J**（Mac）或 **F12** / 右键"检查" → 切到 **Console**
> 2. **Cmd+V** 粘贴（已复制到剪贴板），回车执行
> 3. 若提示不允许粘贴：输入 `allow pasting` 回车，再粘贴一次
> 4. 撤掉改动：执行 `window.__pfhCleanup()`，或直接刷新

同时给出脚本文件的可点击 `file://` 链接，方便日后复用。

**为什么必须走文件 + pbcopy**：聊天窗口会把直引号转成弯引号，用户粘贴后报 `SyntaxError`（真实踩过）。**不要让用户从聊天气泡里复制长脚本。**

### 第 7 步：产出交互说明文档（可选，也可独立触发）

把功能的完整用户流程整理成一份文档里的一张表（写到哪由 [_shared/doc-backend.md](_shared/doc-backend.md) 决定，默认本地 Markdown）：**一个环节一行，写清入口与规则，配一张框好重点的截图**。

**可以不做前 6 步直接进这一步**——手上有个现成功能就能整理，不要求先做过注入。

触发信号：用户说"把这个流程整理成交互文档""每一步截个图说明一下""写份交互说明"，
或刚做完原型、需要把方案沉淀下来（注入刷新即失效，截图才留得住）。

默认表格四列：**阶段 / 入口 / 描述 / 交互**（截图放在交互列，图上用红框标位置）。

四个要点，完整规程见 [references/interaction-doc.md](references/interaction-doc.md)：

1. **先问清流程有几个环节、每个环节从哪进、哪些状态要截图**，并建议用户用画板或流程图工具画出来直接给你消费
2. **先把表格结构发给用户确认再开始截图**——截图最耗时，结构错了全白截；同时给出预计耗时（说实数）
3. **页面上没有的数据就注入 mock 造出来**，这正是本 skill 的本行；造不出来的状态如实标注"需真实环境截取"，不要拿相近的图凑数
4. **用 `scripts/annotate.js` 加红框**，务必检查返回值里的 `found`，定位失败就换方式或出无框图，不要假装框上了
5. **用 `scripts/crop.py` 按返回的 `bbox` 裁剪截图**，并把交互列宽度写进 `<col width>`——整页图塞进默认均分的列会被压到红框看不清，等于白做

写完必须 `docs +fetch` 回读，确认 `<img>` 真的在 `<td>` 内、列宽是自己设的值——命令返回 success 不代表结构正确。
**回读通过后还要在浏览器里打开看一眼**：结构对不等于用户看得清。

### 收尾：沉淀偏好

把本次确认的稳定偏好（执行方式、视觉风格、站点技术栈与危险区、做法禁忌）写入 `<主项目目录>/.product-feature-helper-prefs.md`。格式见 [references/preferences.md](references/preferences.md)。

## 写脚本的硬规则

完整细则见 [references/safety-rules.md](references/safety-rules.md)（崩溃禁区）与
[references/style-contract.md](references/style-contract.md)（样式约束），**写任何注入脚本前必读**。

最容易致命的几条：

| 规则 | 原因 |
|---|---|
| **视觉值只能用 `var(--pfh-*)` token 与 `.pfh-*` 组件类，禁止写颜色/圆角/间距/字号字面量** | 凭感觉写的样式与站点规范不一致，注入后交互割裂——这是本 skill 要解决的核心问题。`deliver.sh` 会扫描并**阻断**违规交付 |
| **改站内既有样式时，正向指定要改的元素，并给 logo / 图标加还原兜底** | `header *` 会把 logo 一起改色；而 `:not(svg)` 挡不住父级 `color` 继承，实测同样失守。必须正向指定 + 品牌元素显式还原（写法见 safety-rules） |
| **禁止**用代码写入富文本编辑器（Slate/ProseMirror/Quill/Lexical/CodeMirror）内容 | 它们维护独立文档模型，外部改 DOM 会导致模型与视图不一致 → **整页崩溃**。换写法只能降低概率、无法根治。只能用剪贴板 + `focus()`，让用户手动粘贴 |
| **禁止**向虚拟滚动列表插入/删除节点 | 打乱其高度与索引计算 → 布局崩坏。新内容另建 `body` 下独立容器 |
| **必须**有幂等清理 `window.__pfhCleanup()`，且要摘监听器、断 observer | 反复粘贴会累积 capture 监听器，抢在自身逻辑前执行，导致**点击"关闭"反而又打开** |
| 拖拽+点击用原生 `click` 判断点击，pointer 事件只管移动 | 单次点击不保证有完整 `pointerdown`/`pointerup` 配对 |
| 框架页面样式走独立 `<style>` 表 | 重渲染会覆盖内联 style |
| 字符串全部用反引号 `` ` `` | 避免复制时直引号被转成弯引号 |
| 多行文本容器加 `white-space: pre-line` | 否则 `\n` 被空白折叠 |
| 能复用站内原生按钮就复用其 `.click()` | 比自己模拟交互安全得多，原生按钮内部会正确处理框架状态 |
| 置顶分档：默认 `z-index`（取 `maxZIndex + 1000`）→ 被站内 popover 盖住时升 Top Layer → 仅被站内 modal 遮挡时才用 `showModal` | `z-index` 只在普通层叠上下文内有效，压不过 Top Layer 里的 popover/dialog。实测对照表见 safety-rules.md。`showModal` 会锁背景交互，不可默认使用 |
| 改站内既有样式必须：量真实高度、叠加原值、备份原内联值以便还原 | 写死高度会遮挡或留白；覆盖原值会破坏布局且无法恢复；回调里不先还原会反复累加 |

## 验证要求

交付前必须完成（前 4 项由 `bash scripts/deliver.sh "$SCRIPT"` 一次性完成）：

1. `node --check` 语法通过
2. 无弯引号
3. **无样式字面量**（违规会阻断交付）
4. token 定义与引用齐备（引用了 `var(--pfh-*)` 就必须含 `:root` 定义，否则变量落空、样式全失效）
5. 含幂等清理逻辑，且改过站内样式的都能被 `__pfhCleanup()` 还原
6. 交付路径与写入路径一致（`ls` 确认文件真的在 `artifacts/` 下）
7. 走方式 A 时：截图确认视觉**与站点风格是否融合** + `console_messages()` 无报错 + 交互实际点一遍

**能在真实页面上跑时，补一遍最小端到端验收**（静态校验过了不等于场景正确）：

- 注入的元素只出现一份，反复执行不叠加
- 开关类交互点两次：开 → 关，状态正确回到初始
- 站内原有内容没被改坏 —— 尤其是选择器写宽了会误伤的地方（logo、导航、标题）
- `__pfhCleanup()` 执行后页面回到注入前，无残留元素、无残留内联样式

**说清楚验证到了哪一步，不要越界**：

| 实际做到 | 只能这么说 |
|---|---|
| 真实页面注入 + 截图 + 点过交互 | "已在你的页面上验证" |
| 只跑了 `deliver.sh` | "静态校验通过，未在页面上实跑" |
| 页面拿不到（受限交付） | "未验证，样式 token 还是空的" |

宁可说"没验证"，也不要把没做过的验证说成做过了。

注意：验证富文本相关功能时，`navigator.clipboard.writeText()` 在脚本模拟点击下会被浏览器拒绝（要求真实用户手势），这是**预期行为不是 bug**，真实用户点击时正常工作，不要据此误判失败。
