## 两种方式的区别（给用户的话术）

询问偏好时必须讲清区别，不要只问"你想要哪种"。建议用如下措辞：

> 两种方式：
>
> **我直接在浏览器里改**——我打开页面、注入代码、截图确认效果，反复微调直到满意，你只看结果。适合改动多、需要来回调整的情况。**需要等一会儿**，因为要多轮"改一版→截图→再调"。另外我需要能访问这个页面（如果要登录，我会请你先手动登录）。
>
> **给你一段 Console 脚本**——我把代码写好交给你，你粘贴到浏览器控制台执行，立刻生效。快、不用等，你也能自己反复调整和保留脚本。但效果我没法亲眼确认，如果不对需要你描述问题、我再改。
>
> 改动比较小或你想自己控制 → 选脚本；改动复杂、想要我调到满意 → 选浏览器直接改。

## 方式 A：浏览器直接改

**执行前告知**："这个需要等一会儿，我会边改边截图确认效果。"

**流程**：
1. `bu.navigate(url)` → `bu.wait_for_load()`
2. 遇登录墙：立即请用户接管浏览器（宿主的接管能力），不要绕路
3. `bu.js(recon.js 内容)` 做侦察
4. `bu.js(注入脚本)` 应用改动
5. `bu.screenshot()` 确认视觉效果
6. 检查 `bu.console_messages()` 是否有报错
7. 交互功能要实际点一遍验证，不能只看截图
8. 不满意 → 回到 4 微调

**验证要点**：
- 截图确认视觉；`console_messages()` 确认无报错；实际点击确认交互
- 验证富文本相关功能时，剪贴板写入被拒是浏览器安全策略（需真实用户手势），不是 bug
- 用脚本内部触发点击来验证逻辑，可排除坐标失效的干扰

**同时保留脚本**：即使走方式 A，也要把脚本存成本地文件。页面一刷新注入就消失，用户需要脚本才能自己恢复。

## 方式 B：Console 脚本

**核心风险：智能引号**

聊天窗口渲染代码块时可能把直引号（`'` `"`）转成弯引号（`'` `'` `"` `"`），用户粘贴后报 `SyntaxError`。**这是实际发生过的问题。**

**双重防线**：
1. 脚本内字符串**全部用反引号** `` ` ``，不易被转换
2. **不让用户从聊天气泡复制长脚本**，走本地文件 + `pbcopy`

**交付流程**：

落盘路径是强制的：`<主项目目录>/artifacts/pfh-<简短功能名>.js`。

```bash
# 路径定义一次，写入 / 校验 / 交付链接全程复用同一个值
SCRIPT="<主项目目录>/artifacts/pfh-<功能名>.js"

bash scripts/deliver.sh "$SCRIPT"
```

脚本会校验语法、扫描弯引号、检查清理逻辑、阻断样式字面量，然后复制到剪贴板。

**调用方式**：始终 `bash deliver.sh ...`，不要 `./deliver.sh`。执行位在打包、解压、
跨平台 clone 后可能丢失，显式用 `bash` 不受影响。遇 `Permission denied` 直接换
`bash` 调用，不必 `chmod`。

**剪贴板不可用不是失败**：脚本依次尝试 `pbcopy / wl-copy / xclip / xsel /
clip.exe / powershell`，服务器与容器里常常全都没有。此时它打印文件路径和手动复制
步骤，**退出码仍为 0**，校验结论完全有效。把文件给用户即可，不要因此重试或换方案。

**路径漂移是实测中最高频的工具层失败**：写入用了一个路径、校验又拼了另一个，
于是报 `MODULE_NOT_FOUND` / 文件不存在，再靠移动文件和重跑补救。
**校验失败时先 `ls` 看文件实际在哪，不要直接改路径重试。**

**给用户的操作说明**（必须完整给出）：
> 1. 在目标页面按 **Cmd+Option+J**（Mac）或 **F12** / 右键"检查" → 切到 **Console**
> 2. **Cmd+V** 粘贴（我已复制到剪贴板），回车执行
> 3. 如果 Console 提示不允许粘贴：输入 `allow pasting` 回车，再粘贴一次（Chrome 的一次性安全确认）
> 4. 想撤掉改动：执行 `window.__pfhCleanup()`，或直接刷新页面

同时给出文件路径，方便用户之后重复使用。

## 失败降级：A → B

**触发条件**（任一即降级）：
- 浏览器工具/扩展连接失败
- 无法访问目标页面（登录接管后仍失败）
- 同一注入连续两次失败且原因不在代码本身

**不构成降级理由**（这些是环境差异，不影响交付有效性）：
- 剪贴板工具缺失 → 给文件路径 + 手动复制步骤即可
- `deliver.sh` 报 `Permission denied` → 改用 `bash deliver.sh ...`
- `node recon.js` 报 `document is not defined` → 本就该在浏览器里跑，换正确方式

**关键规则：同一个失败不要反复硬试。** 实测中曾连续重试 5 次同样的连接错误，纯属浪费用户时间。**失败 2 次就降级。**

**降级话术**（如实说明，不含糊）：
> 浏览器这边连不上（是工具连接层的问题，不是页面问题），我没法直接帮你改了。
> 脚本我已经写好了，你粘贴到 Console 就能看到效果。

**注意措辞**：如果降级前**没能侦察页面**，就不要说"一样的效果"——没提取过 design system 的
脚本，样式大概率和站点不一致。这种情况如实说：

> 没能连上页面做侦察，所以样式 token 是空的，这版粘上去结构能用、视觉可能和站点不搭。
> 你在 Console 跑一下 `design-system.js` 把 `copy(window.__uiDS.cssText)` 回传给我，我补齐。

然后立刻按方式 B 交付完整脚本。**不要把降级说成"建议你自己试试"**——是工具受限，不是用户的问题。

**用户明确说了不想自己贴脚本时**（"你直接帮我改""我不会弄这个"）：
这是用户约束，不能无视。优先请他协助打通页面访问——请他接管浏览器
请他登录或接管浏览器，让方式 A 走得通；实在打不通再给脚本，并说明为什么只能这样：

> 你说不想自己贴脚本，我理解。但现在页面我这边访问不了（需要登录态），
> 你帮我在浏览器里登录一下，我就能直接改完给你看效果。
> 如果不方便，我只能给脚本让你粘一次——只需要粘一次，之后我再调都不用你动手。

**不要**在用户已经说"不想自己贴"之后，一声不吭地还是把脚本丢过去。

同时，如果排查出可操作的原因（如插件账号不一致、需完全重启浏览器），一并告知，但不要让用户在无进展的重试里反复消耗。
