# 第 7 步：产出交互说明文档

把一个功能的完整用户流程，整理成一份文档里的一张表：**每个环节一行，说清入口、规则，配一张框好重点的截图**。

产出的是给研发/设计/评审看的交互说明，参照常见 PRD 里「交互设计」章节的写法。在 ai-pm 流程里，这份文档是 `pm-prd` 组装 PRD 时「交互设计」一节的来源。

## 什么时候用

**可以独立触发**，不要求先做过前 6 步：

- 刚用前 6 步做完原型 → 顺手把交互整理成文档
- 手上就有个现成功能（自己的或别人的）→ 直接进第 7 步，跳过注入
- 用户说"把这个流程整理成交互文档""每一步截个图说明一下""写份交互说明"

**前 6 步做过注入时的额外价值**：注入的原型刷新就没，但截图能留下来。做完原型顺手出一份，方案才留得住。

## 表格结构

默认四列，够用且通用：

| 列 | 放什么 |
|---|---|
| **阶段** | 用户处在流程的哪一步。同一阶段有多个入口时，这一列跨行合并 |
| **入口** | 从哪进来——按钮名、菜单路径、预制 prompt、URL |
| **描述** | 用户诉求 / 用户动作 / 规则逻辑 / 判定条件 |
| **交互** | 截图，图上用红框标出要看的位置 |

描述列建议用加粗小标题分层，读起来清楚：

```
<b>用户诉求：</b>想快速了解这个工具怎么用
<b>用户动作：</b>进入首页，点击「了解使用方式」
<b>阶段判定：</b>当用户还没创建任何岗位时
```

**需要额外列时才加**，不要默认加：涉及配置项就加「输入&输出」放 JSON，涉及多角色就在描述列里用 `<b>角色：</b>` 分段。

## 完整流程

### 7.1 先问清楚流程有几个环节

一次问完，不要挤牙膏：

> 我来把这个功能的交互整理成文档。先跟我说说：
>
> 1. **用户流程是什么样的，分几个环节？**（比如：进入首页 → 点击入口 → 填写表单 → 看到结果）
> 2. **每个环节从哪进去？**（按钮名、菜单位置都行）
> 3. **哪些状态需要截图？** 包括正常态，也包括空态、加载中、报错这些——**没数据的状态我可以注入假数据造出来**，不用担心页面上没有
>
> 如果流程比较复杂，**你可以用画板或流程图工具画出来直接发我**，我读画板比读文字准。画的时候把每个节点对应的按钮名字写上，我好定位截图位置。

**画板的处理**：用户给了画板链接就先读，把节点、连线、文字提取出来，转成环节列表再跟用户确认。别直接拿画板当最终结构——画板通常只有节点名，没有规则描述。

### 7.2 拿结构给用户确认

**先给结构，再动手截图。** 截图是整个流程里最慢的一环，结构错了全部白截。

把整理出的表格**以纯文本形式**发给用户看：

> 结构我整理成这样，你看对不对（截图位置我标了序号）：
>
> | 阶段 | 入口 | 描述 | 交互 |
> |---|---|---|---|
> | 1. 进入首页 | 直接访问 URL | 用户动作：… | 待截图① 首页默认态 |
> | 2. 点击了解使用方式 | 首页底部按钮 | 用户诉求：… | 待截图② 展开后的回答 |
>
> 确认没问题我就开始截图。**大概需要 X 分钟**（按每张 1～2 分钟估，说个实数别说"一会儿"），做好我把文档链接发你。

用户确认后再进 7.3。**这一步不能省**——它是唯一一次低成本纠错的机会。

### 7.3 逐个状态截图

见下方[截图](#截图怎么到达那个状态)、[红框标注](#红框标注)、[裁剪](#裁剪整页截图直接放进表格等于白做)三节。
**裁剪不能跳过**——整页图放进表格会被压到看不清。

### 7.4 建文档、写表格

见[写入文档](#写入文档)。

### 7.5 交付

给出文档链接，并说明：

- 一共几个环节、几张图
- **哪些图是注入 mock 数据造出来的**（必须说，别让人以为是线上真实状态）
- 哪些状态没能截到、为什么

## 截图：怎么到达那个状态

难点从来不是截图本身，是**怎么让页面进入那个状态**。按顺序尝试：

| 状态类型 | 做法 |
|---|---|
| 页面默认态 | 直接 `bu.navigate` → 截 |
| 点击后出现（弹窗、下拉、展开） | 找到元素 `.click()` → 等渲染 → 截 |
| 需要填表才出现 | `bu.type` 填入 → 触发 → 截 |
| **没有数据的空态 / 列表态 / 结果态** | **注入 mock 数据造出来**（见下） |
| 加载中 / 报错态 | 注入覆盖层模拟，或拦截请求 |

### 用注入造状态（本 skill 的看家本事）

页面上没有真实数据不是障碍——**交互文档展示的本来就是交互，不是真实业务数据**。

造状态时守住两条已知禁区（详见 [safety-rules.md](safety-rules.md)）：

- **虚拟列表**：不要往列表里插节点，改成在 `body` 下另建 `position:fixed` 容器叠在原位置
- **富文本编辑器**：不要用代码写入内容

推荐做法是复用 `injection-template.js` 的骨架，配合第 2 步提取的 `DS_CSS`，
让造出来的 mock 数据在视觉上和站点一致——**mock 数据长得不像站里的东西，截图就没有说服力**。

mock 内容用**明显是示例但不荒诞**的数据：人名用「张三」「李四」，公司用「某某科技」，
不要用「测试123」「aaa」这种一眼假的，也不要用真实用户数据（有隐私风险）。

### 截不到就如实说

状态确实造不出来（依赖特定权限、依赖后端返回、跨域 iframe 内），
在表格该行的交互列写明「**该状态需在真实环境截取**」，并在交付时单独列出来。
**不要拿一张相近的图凑数**。

## 红框标注

用 `scripts/annotate.js`，把"要看哪里"直接拍进截图。

```javascript
// 1. 注入脚本（bu.js 传入文件内容）
// 2. 调用标注
__pfhAnnotate([
  { text: `了解使用方式`, label: `1`, note: `点击进入` },   // 按可见文本找（最稳）
  { selector: `.entry-btn`, label: `2` },                    // 按选择器找
  { rect: {x:100,y:200,w:180,h:40}, label: `3` }             // 直接给坐标（兜底）
]);
// 3. 截图
// 4. __pfhAnnotateClear()  清除，再进入下一个状态
```

**返回值一定要看**：每项都带 `found`。

```json
[{"label":"1","found":true,"by":"了解使用方式"},
 {"label":"2","found":false,"by":".entry-btn"}]
```

`found: false` 表示没定位到，那一项**没有框**。此时：
1. 换定位方式重试（文本 → 选择器 → 坐标）
2. 还是不行就出无框截图，并在描述列用文字说明位置
3. **不要假装框上了**

**定位优先级**：可见文本 > `aria-label` / `role` > 稳定类名 > 坐标。
构建后带哈希的类名（`xxx__1RKMF`）会变，别写死。

标注脚本只在 `body` 下加 `position:fixed` 覆盖层，`pointer-events:none`，
不碰站内 DOM，`__pfhAnnotateClear()` 后页面完全复原。

## 裁剪：整页截图直接放进表格等于白做

**这一步不能省。** 表格的交互列最宽也就 500 多像素，整页截图（常见 1000+ 宽）塞进去会被压到
30% 以下，红框和序号全糊，文档就失去了意义——实测出现过缩到 20%、完全看不清的情况。

`__pfhAnnotate()` 的返回值里带 `bbox`，就是所有标注的包围盒（已含 24px 留白）：

```json
{"items":[...],
 "bbox":{"x":490,"y":153,"w":241,"h":86,
         "viewport":{"w":775,"h":760},"dpr":2}}
```

拿它调 `scripts/crop.py`：

```bash
python3 scripts/crop.py <原图> <输出> <x> <y> <w> <h> [scale] [min_w] [min_h] [max_w]
# 例：交互列按 520 设计，就让图最终宽度也是 520
python3 scripts/crop.py shot.png s1.png 490 153 241 86 1 520 300 520
```

- `min_w/min_h`：太小的标注会向四周扩展，保证画面有上下文，不是贴着框硬切
- `max_w`：超出就等比缩小，让**图片原始宽度直接等于目标显示宽度**

**scale 默认 1，通常不要改。** `bbox.dpr` 常报 2，但浏览器截图输出的往往已是 CSS 像素，
乘 dpr 会让坐标越界、裁出错误区域（实测裁出过 114×640 的废图）。
判断方法：比对截图实际宽高与 `bbox.viewport`，一致就用 1。

### 标注跨度过大时，缩放不是解法

若多个红框水平跨度接近整个视口，硬缩到列宽会把小字压糊。两个选择：
1. **放宽交互列**，前几列压窄（文档总可用宽约 820px）
2. **拆成两行**，一行标一处

不要靠缩放硬塞——缩完看不清，等于没标。

## 写入文档

写到哪由 [../_shared/doc-backend.md](../_shared/doc-backend.md) 决定：**默认写本地 Markdown**（表格 + 相对路径引用截图，零配置）；用户要放到云文档时，按那里的规则问一次后端并记住。

无论哪个后端，下面几条都要守住：图片在表格单元格内、交互列宽度显式设置并与裁剪宽度一致、写完回读确认结构、最后在渲染后的页面上看一眼。

### 以飞书 / Lark 为后端（已验证）

**已验证可行**：图片可以放进表格单元格。步骤：

1. **截图落成本地文件**
2. **上传拿到公网 URL**（用文件上传能力，得到 `https://...` 链接）
3. **建文档**
   ```bash
   lark-cli docs +create --title "<功能名> 交互说明" --as user
   ```
4. **写入表格**：`<img href="URL"/>` 放在 `<td>` 里
   ```bash
   lark-cli docs +update --doc <doc_id> --command append --content @table.xml --as user
   ```

表格 XML 的形状（这段实测写入成功、图片确实落在单元格内）：

```xml
<table><colgroup>
  <col width="76"/><col width="94"/><col width="130"/><col width="520"/>
</colgroup>
<thead><tr>
  <th background-color="light-gray"><p>阶段</p></th>
  <th background-color="light-gray"><p>入口</p></th>
  <th background-color="light-gray"><p>描述</p></th>
  <th background-color="light-gray"><p>交互</p></th>
</tr></thead>
<tbody>
<tr>
  <td vertical-align="top"><p>1. 进入首页</p></td>
  <td vertical-align="top"><p>直接访问 URL</p></td>
  <td vertical-align="top"><p><b>用户诉求：</b>了解怎么用</p><p><b>用户动作：</b>点击「了解使用方式」</p></td>
  <td vertical-align="top"><img href="https://图片URL"/><p>红框为点击位置</p></td>
</tr>
</tbody></table>
```

### 列宽必须显式设置

**`<col/>` 不写 `width` 时飞书会平均分配**，四列各约 200px，交互列的截图会被压到看不清。
文档可用宽约 **820px**，按「文字列压窄、交互列吃满剩余」分配：

| 列 | 建议宽度 |
|---|---|
| 阶段 | 76 |
| 入口 | 94 |
| 描述 | 130 |
| **交互** | **520** |

交互列的宽度要和上一节 `crop.py` 的 `max_w` 取同一个值，图片才不会被二次压缩。

**`<img width="...">` 不可靠**：实测写了 400，回读仍是原始像素宽。
所以不要指望这个属性，直接让图片文件本身就是目标宽度。

**同一阶段多个入口**用 `rowspan` 合并阶段列：`<td rowspan="2">`。

**内容里有 `&` `<` `>` 要转义**，否则 XML 解析失败。

### 写完必须回读验证

```bash
lark-cli docs +fetch --doc <doc_id> --detail with-ids --as user
```

逐项确认，**不要只看命令返回 success**：

- `<img>` 是否在 `<td>` 内（不在就是被挤到表格外了）
- `<col width>` 是否是自己设的值（被平均分配就说明没生效）
- 图片数量与预期一致
- 行数与环节数一致

写入命令返回 `success` 只代表请求被接受，不代表结构正确。

### 还要看渲染层

**结构对不等于好用。** XML 回读只能证明标签在正确位置，证明不了用户打开时看得清。
真实踩过：结构全对、图片都在 `<td>` 里，但列宽平均分配导致截图缩到 20%，红框完全不可辨。

所以最后必须**在浏览器里打开文档看一眼**：图片是否清晰、红框是否可辨、列宽是否合理。
这一步用截图确认，不能靠推断。

## 失败与降级

| 情况 | 怎么办 |
|---|---|
| 页面登录不了 | 请用户接管浏览器，不要跳过；宿主不支持接管时直接说明需要手动登录 |
| 某个状态造不出来 | 该行写明"需真实环境截取"，其余照常产出 |
| 标注定位失败 | 换定位方式；仍失败则出无框图 + 文字说明位置 |
| 图片上传失败 | 重试一次；仍失败则先出纯文字表格，图片后补 |
| 云文档创建失败 | 先把表格 XML 存成本地文件交给用户，不要丢掉已截的图 |

**共同原则**：已经完成的部分不要因为某一环失败就整体放弃。截了 8 张图卡在第 9 张，
就把 8 张先写进文档，第 9 行标注待补。
