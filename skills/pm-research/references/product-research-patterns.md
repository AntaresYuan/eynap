# 产品调研报告范式 — 按对方的业务流程走查，再回到自己的决策

从一份真实、高质量的对标产品调研报告中抽出的**调研节奏**与**产出文档的故事线**。这份调研和竞品分析结构几乎一样，唯一区别是**不论证"为什么它是竞品"**——范围是给定的，直接进入走查。

> 本文只保留方法与写法，业务细节已脱敏。示例中的产品名、团队名、字段与数字均为占位。

## 这份调研和普通竞品分析的区别

| | 普通竞品分析 | 这种产品调研 |
|---|---|---|
| 范围 | 要先论证"为什么算竞品" | **范围给定，不做竞品资格论证** |
| 主线 | 按我方的问题清单逐个比 | **按对方的完整业务流程逐环走查** |
| 落点 | 对比表 + 空白结论 | **每个功能点直接给出"学/不学/中性 + 怎么搬"** |

所以它更像一次**对标产品的全流程逆向**，而不是一张特性对比表。

## 调研节奏：八步

### 0. 先定「调研目的」，目的没定不开工

**这是排在所有步骤之前的一步，也是决定后面结论有没有用的一步。** 先回答一个问题：**这次调研完成后，要支持什么决策？**

- "摸清这条技术路径当前的真实能力边界，为我们自己的系统设计提供参考" —— 能力研究
- "决定要不要采购 / 引入这个产品" —— 选型
- "判断这个方向值不值得做" —— 方向判断

**目的不同，后面的问题、实验和结论写法全不同。** 能力研究要的是机制拆解和边界，选型要的是成本与落地风险，方向判断要的是空白与时机。目的模糊就开工，最后会得到一份"什么都查到了、但什么决策都支撑不了"的文档。

目的定下来后，**用它反向约束调研范围**：

1. 把目的拆成 2–4 个**具体问题**（"它准不准""够不够智能""能不能捞干"），每个问题都要能直接对应一个结论。
2. 明确**这次不回答什么**——划掉的范围写进方案的"未覆盖"节，而不是假装覆盖了。
3. 不同功能如果测法不同，**在这一步就分开立项**。一次性搜索和持续自动推荐是两个东西，用同一套问题问，结论必然含糊。

### 1. 先对齐「问题定义」，而且要写两种

在调研目的之下，再并排写**他们定义的问题**和**我们定义的问题**，列差异与共性。

为什么必须做这一步：**同一个业务，对方和你对"要解决什么问题"的定义很可能不同。** 带着自己的问题定义去看对方的解法，会系统性误读——你以为它在解决 A，其实它在解决 B，而 B 你根本不关心，或者恰恰该关心。

对齐之后立刻补三件事，作为全篇的判断基准：

- **对方的范围**：从哪一步到哪一步
- **对方的成功定义**：它成立的标准是什么
- **对方的盈利模式 / 约束**：它怎么收费，决定了它为什么这样设计

### 2. 画一条共同的业务漏斗

在进入任何细节前，先放一张**双方共用的业务漏斗图**（白板即可）。后面所有章节都挂在漏斗的环节上，而不是按对方的产品菜单组织。

这一步的作用是给全篇一个**与对方菜单无关的坐标系**：对方的功能再乱，也能被映射回一条主流程链。

### 3. 按漏斗环节逐环走查，顺序与主流程一致

每个环节一个一级标题，**顺序严格沿主流程**，不要按功能酷不酷排序。每个环节内部固定回答两段：

1. **本环节要解决的问题** —— 先写问题，再看解法。
2. **他们的动作** —— 对方在这一环做了什么，拆到具体功能点。

主线之外的页面和底座能力单独成章，不混进主流程。

### 4. 不只走查功能，还要设计实验去量化它的真实表现

**纯功能走查只能回答"它有没有这个功能"，回答不了"它做得好不好"。** 一个功能演示流畅，和它在真实任务上结果可靠，是两件事。对关键能力，必须在走查之外**单独设计实验**，用对照和量化证据说话，而不是凭操作手感下判断。

实验方案在动手跑之前先写定，顺序如下：

**4.1 先写死前置约束——约束决定实验只能怎么设计。**
诚实列出测不了什么。例如：对方是外部黑盒、看不到库内全集 → **只能测"推出来的对不对"，测不了"该有的有没有被漏掉"**；对方数据源覆盖的是某个地区 → 就不能拿另一地区的样本测，否则测出来的是"数据覆盖问题"而不是"产品能力问题"。约束不写明，后面的数字会被误读。

**4.2 单变量对照设计实验组。**
每组只改一个东西，差值才能归因：

| 组 | 输入 | 测的净差异 |
|---|---|---|
| 基线 | 原始材料直接喂 | 它能否从噪音里提取有效条件 |
| 去噪组 | 只做去噪重组、**严格不增加原材料没有的信息** | 与基线之差 = 表述质量的净收益 |
| 专用入口组 | 与基线完全相同的输入，换入口 | 与基线之差 = 专用通道的净收益 |
| 手动干预组 | 与去噪组一字不差，只手动改系统生成的条件 | 手动改的那个条件到底生不生效 |

两条关键纪律：

- **去噪组"严格不加信息"**：一旦加了原材料没有的条件，差值就同时混入"表述质量"和"信息量"两个变量，无法归因。
- **手动干预组输入一字不改、改完截图留证**：它不是新输入实验，而是在既有结果上做单点干预；重新提交可能触发系统重算、覆盖手改值，导致结论作废。

**4.3 预先定判定标准，不能边看结果边定。**
对每条结果用固定量表分档（如 可推进 / 部分匹配 / 不匹配 / 信息不足），再配几个池子级量化指标（命中总量、某个硬约束的执行占比、组间结果重叠率）。**量表和指标在实验前定死**，看完结果再改标准等于自证。

**4.4 选样本要专门挑"能戳中机制弱点"的。**
样本不是随便选一个。选那种**资格判定依赖"做过什么事"而不是"职位叫什么名"**的案例——如果对方的机制是把自然语言压成类目化关键词，这类样本会让它的缺陷系统性暴露，比选一个普通案例有信息量得多。

**4.5 用探针法测"持续型"功能，而不是只看一次结果。**
一次性搜索看返回列表即可；但带反馈循环、持续自动运行的功能，要设计**探针**：分别喂"客观硬条件"和"主观软偏好"两类反馈，观察它是否据此收敛、一轮能砍掉多少、几轮稳定，单位是**校准轮次**而不是日历天数。

**4.6 明写"本次没测什么"。**
漏放没做种子验证、长期行为需要数周、某环节没实际执行——这些都要在方案里先声明。**没测的东西不能写成结论**；机制推断要和抽样实测分开标注。

> 走查（第 3 步）回答"它做了什么、怎么做的"，实验（本步）回答"它到底行不行"。两者缺一不可：只有走查会被演示骗，只有实验会知其然不知其所以然。

### 5. 每个功能点同时收集一线反馈与实验证据，分开两列、绝不混写

- **一线反馈** —— 真实使用者怎么说，优点缺点都要，带原话与来源
- **实验实测** —— 第 4 步设计的实验结果，以及随手操作中发现的"能跑通 / 跑不通 / 与宣称不符"

两类证据分开列。**实测专门用来抓"官方说有、实际不行"的落差**，而实验专门回答"在标准化任务上它有多可靠"。

### 6. 每个功能点当场给判断，而不是堆到最后

走查时就对每个功能点贴一个判定，不等全篇看完：

| 判定 | 含义 |
|---|---|
| **可借鉴** | 机制值得搬，但要说明搬什么、改什么 |
| **中性** | 思路对但属于已有基建，或与我们场景无关 |
| **我们更好** | 对方做法不如我们已有的/计划的 |

判定后面永远跟一句"**对我们来说**"——把对方的设计翻译成我们自己的处境，这是全篇出现频率最高的一个句式。**调研的价值不在描述对方，在每一处都落回"那我们呢"。**

### 7. 对重点环节做专项深挖，独立成子文档

主文档保持"一环一节"的节奏；**当某个环节值得投入时，开一个专项子文档**深入，主文档里用引用挂接。深度评测（带实验的那类）也独立成子文档。

专项文档的标准结构（这个结构本身可复用）：

1. **一句话结论**（用 callout 置顶）：要不要搬、搬哪一层、不搬哪一层。判断要具体到"搬输入层，不搬功能形态"这种粒度，不能是"值得学习"。
2. **该学的几块**（表：该学什么 / 它怎么做 / 我们怎么搬）
3. **不该学的几块**（表：不该学什么 / 问题在哪 / 怎么处理）
4. **搬之前必须先确认的前提**（表：确认什么 / 为什么是前提 / 怎么确认）
5. 功能实录走查（含对方原始模板/流程的完整记录）
6. 设计拆解与可抄清单
7. **尚未验证的问题** —— 明确列出，不假装都跑通了

**带实验的评测子文档**在结论之后、原始记录之前，还要放一节完整的「实验方案设计」：评测目标与产品定位 → 前置约束 → 样本选择理由 → 单变量对照组 → 预先定死的判定标准 → 本次未覆盖范围 → 执行情况。**先有方案再有结果，结论才可复核。**

### 8. 原始记录全部沉到附录

正文里只放判断与关键证据；**逐字的一线反馈、逐条实验与实测原始记录放到附录**，按漏斗环节组织。正文的每个判断都能在附录找到出处，附录不替正文下结论。

## 产出文档怎么讲故事

这份文档的说服力来自它的**叙事顺序**，不是信息量大。故事线是：

```
这次调研要支持什么决策？—— 先定目的，目的约束后面所有问题
        ↓ （能力研究 / 选型 / 方向判断，不同目的问不同问题）
我们和他们要解决的，是不是同一个问题？
        ↓ （对齐问题定义，摆差异）
在同一条业务链上，他们一环一环是怎么做的？
        ↓ （沿漏斗走查，每环先讲问题再讲解法）
它到底行不行，而不只是「有没有」？
        ↓ （实验：前置约束 → 单变量对照 → 预先定死的判定标准）
每一处，我们该学、不该学、还是本来就更好？
        ↓ （当场判定，落回"对我们来说"）
重点环节具体怎么搬？
        ↓ （专项子文档：结论 + 该学/不该学 + 前置条件）
所以最后，要动手做哪些事、按什么优先级？
        ↓ （可抄清单 P0/P1/P2/不抄）
```

三条叙事纪律：

**1. 结论先行，且结论是"动作"不是"评价"。**
子文档第一句就是"要搬，搬输入层不搬参会形态"，不是"这是一个设计精良的功能"。读者看完第一句就知道该不该投入。

**2. 每个"该学"都配一个"不该学"。**
只讲该学的，会让团队照搬整个功能，包括它最大的坑。报告里最有信息量的一条往往是"**机制好，但它把这个价值锁死在一个人身上**"——实时回显是好的，只给发起人看是错的，所以"否掉的是单人可见，不是实时本身"。这种**把机制和实现方式拆开评判**的写法，是这份调研的精髓：学机制，改掉那个错误的实现选择。

**3. 每个借鉴都要回答"搬到我们这会遇到什么不一样"。**
对方的前提（数据规模、合规环境、用户角色、基建）和你不同，直接抄会失败。所以专项结论后必须跟"**搬之前必须先确认的两件事**"——通常是数据能力是否支持、对方的实现是硬编码还是真通用。这一节防止"抄回来才发现地基没有"。

## 一个功能点的标准写法

正文表格固定五列，这是节奏落到纸面的最小单元：

| 列 | 写什么 |
|---|---|
| **环节 / 对象** | 这个功能点的名字 |
| **说明** | 判定标签（可借鉴/中性/我们更好）+ 三段：**解决的问题** / **对用户的价值** / **对我们来说**（含可借鉴点或差异） |
| **界面** | 截图，关键处可多图并排 |
| **一线反馈** | 真实使用者的原话，优缺点分列，无则填 `-` |
| **实验实测** | 自己跑的结果，能跑通什么、哪里与宣称不符，无则填 `-` |

「说明」列里的三段是强制的，且顺序不能乱：**先讲问题，再讲对用户的价值，最后才轮到我们怎么看。** 跳过问题直接夸功能，会变成功能介绍而不是调研。

## 结论怎么落地成动作

全篇最后（或专项文档末尾）给一张**可抄清单**，按实施优先级排：

| 优先级 | 归属 | 可抄的设计 | 说明 |
|---|---|---|---|
| **P0 / P1 / P2** | 功能模块 | 具体到可实现的设计点 | 为什么是这个优先级、搬的时候要改什么 |
| **不抄** | — | 对方的某个设计 | 不抄的原因（通常是机制对但实现错，或合规硬卡点） |

这张表是整份调研**唯一直接对接排期**的部分。它把"该学的几块"翻译成一条条带优先级的工程项，并显式保留一个"**不抄**"分区——不抄也要写明，防止后来者看到对方有就又加回来。

## 证据分层：正文判断、附录原始记录

| 层 | 放什么 | 谁读 |
|---|---|---|
| **正文** | 每个功能点的判断 + 最关键的一两条证据 | 决策者、评审 |
| **专项子文档** | 重点环节的完整论证与可抄清单 | 要动手实现的人 |
| **附录** | 一线反馈原话、逐条实测原始记录，按环节组织 | 想复核结论的人 |

三层的关系是：**正文下结论，专项给论证，附录存证据。** 正文的每个"可借鉴/不借鉴"都必须能在附录追溯到一句一线反馈或一条实测结果；附录只记录，不抢着下结论。

证据强度同样分级（沿用 `pm-research` 的规则）：**实验量化结果 > 实测跑通 > 一线反馈 > 对方官方宣称**。官方文档写了但自己没验证的，只能标"对方称"，不能写进"实验实测"。

### 评测方法本身也要复盘

评测做完，单独留一节写**方法上的教训**——这一步常被跳过，但它决定下一次能不能测得更准。真实踩过的两类：

1. **降权 / 隔离类问题必须读判定理由全文，不能只看结果名单的构成。** 名单前几名干净，不构成"隔离能力成立"的证据；抽样读一小批得出的比例，和全量读完可能完全相反。
2. **漏放无法靠看名单测量。** 被漏掉的对象不在结果里，看名单只能测准确率。严格测漏放要用**种子探针法**：自选确定合格的对象，观察能否被推出；没推出的再单独按名字检索一次，以区分"系统漏放"和"库里本来就没有"。

### 适用性限制要在结论里明说

评测结论受样本和数据源约束，**不能外推到没覆盖的场景**。样本是为某个地区/某种条件选的，就要在结论开头写明"本结论不代表另一地区/另一数据源下的表现；数据覆盖是独立于算法能力的前置问题"。否则读者会拿一个局部结论去支持全局决策。

## 反模式

- ❌ **开篇介绍对方公司和融资情况。** 开篇应该是双方问题定义对齐，不是背景资料堆砌。
- ❌ **按对方的产品菜单组织章节。** 要按双方共用的业务漏斗组织，否则读完得到一张功能地图而非一条可决策的链。
- ❌ **只描述对方做了什么，不写"对我们来说"。** 没有这一句就不是调研，是翻译。
- ❌ **通篇只夸该学的，没有"不该学"。** 最有价值的判断往往是"机制对、实现错"。
- ❌ **结论是"值得学习"这类评价。** 结论必须是动作：搬哪一层、不搬哪一层、搬之前先确认什么。
- ❌ **只看官网和文档，不亲手测、不找一线反馈。** "专门做的入口不如直接粘贴原始材料"这类结论只有实测能得到。
- ❌ **把原始记录堆在正文。** 正文放判断，证据沉附录。
- ❌ **抄方案前不查自己的地基。** 数据能力、合规、用户角色不同，直接搬一定返工。
- ❌ **用大词下判断**（"赋能""闭环""生态化反"）。调研结论要能直接变成工程项，措辞规范见 [../../_shared/verification.md](../../_shared/verification.md)。
